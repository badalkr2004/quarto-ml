Lecture 39 — OAuth 2.0, OIDC & PKCE

Google login without taking Google passwords (in plain words)

Author

Practice notes based on Aditya Tandon (Coder Army)

Video: OAuth 2.0 Masterclass | Google Login, OIDC & PKCE | Full Course #39
Playlist index: 39
Builds on: Lecture 38 (tokens & trust)

Big idea in one line

“Login with Google” does not mean users type their Google password into your app.
Google authenticates them; your app receives permission (and identity) through a standard protocol: OAuth 2.0 (+ OpenID Connect for “who is this user?”).

User → Your app → redirect → Google login + consent
                         ← redirect back with code
Your app ↔ Google        exchange code → tokens
Your app                 create local session / your JWT

Topic 1 — Why not collect Google passwords?

If users gave you their Google password, you could open Drive, Photos, Mail, …
Nobody should do that. OAuth exists so Google stays the identity provider; you only get scoped access the user approved.

Topic 2 — Main actors

Actor Plain role
Resource owner The user
Client Your application
Authorization server Google (login + consent + codes/tokens)
Resource server Google APIs (Calendar, …) when you call them with an access token

Topic 3 — Scope and consent

Scope = what you ask for (openid, email, profile, or API scopes like calendar read).

Consent = Google shows the user a screen: “Allow this app to …?”

Ask fewer scopes → easier consent → less risk
Ask powerful scopes → user may refuse

Topic 4 — OAuth vs OpenID Connect (OIDC)

OAuth 2.0 OpenID Connect
Main job Authorization — allow access to resources Authentication — prove who logged in
Typical token Access token ID token (+ often access token too)
Question answered “What may this client do?” “Who is the user?”

For “Sign in with Google,” you want OIDC (login), not only “call Google Calendar.”

ID token     → for your app (identity claims: sub, email, …)
Access token → for calling Google APIs (if scopes allow)

Topic 5 — Authorization Code flow (browser apps)

Common happy path:

  1. User clicks “Continue with Google”
  2. Browser redirects to Google with client_id, redirect_uri, scope, state, …
  3. User logs in + consents
  4. Google redirects to your redirect_uri with an authorization code (+ state)
  5. Your backend exchanges the code for tokens (server-side, with client secret when using confidential clients)
  6. You create your own logged-in state (session or your JWT)

state parameter: random value you send and verify on return → helps stop CSRF on the redirect.

Topic 6 — PKCE (why mobile / public clients need it)

PKCE (“pixy”) protects the authorization code when a client cannot keep a secret safe (SPA / mobile).

Before redirect:
  create code_verifier (random)
  create code_challenge = hash(verifier)
  send challenge to Google

Token exchange:
  send code + code_verifier
  Google checks verifier matches earlier challenge

Even if an attacker steals the redirect code, they lack the verifier → exchange fails.

Topic 7 — Practice lab (IDE + Google Cloud)

Step 1 — Google Cloud credentials

  1. Open Google Cloud Console
  2. Create / select a project
  3. Configure OAuth consent screen
  4. Create OAuth client ID (Web application)
  5. Add authorized redirect URI matching Spring’s callback (often something like http://localhost:8080/login/oauth2/code/google)
  6. Copy Client ID and Client Secret

Step 2 — Boot dependencies

  • Spring Web
  • Spring Security
  • OAuth2 Client (spring-boot-starter-oauth2-client)

Step 3 — application.properties (shape)

spring.security.oauth2.client.registration.google.client-id=YOUR_ID
spring.security.oauth2.client.registration.google.client-secret=YOUR_SECRET
spring.security.oauth2.client.registration.google.scope=openid,profile,email

(Exact property names follow Boot’s OAuth2 client registration format.)

Step 4 — Security config

http
  .authorizeHttpRequests(auth -> auth
      .requestMatchers("/", "/error").permitAll()
      .anyRequest().authenticated()
  )
  .oauth2Login(Customizer.withDefaults());

Step 5 — Test

  1. Run app → open a protected URL
  2. Redirect to Google → login → consent
  3. Land back authenticated
  4. Inspect principal / attributes (email, sub) in a controller

Step 6 — Connect to your own JWT (optional bridge)

Many APIs still issue your JWT after Google login succeeds, so mobile clients talk to you the same way as password login.

Topic 8 — Safety checklist

Do Don’t
Use HTTPS in real environments Put client secrets in front-end JS
Verify state Ask for every Google scope “just in case”
Store secrets in env / secret manager Log ID tokens / access tokens
Understand redirect URI must match exactly Treat OAuth as “share Google password with us”

Short map to keep

OAuth 2.0  → authorization (access token + scopes + consent)
OIDC       → authentication (ID token = who)
Auth code  → browser redirect dance
PKCE       → protect public clients during code exchange
Spring     → oauth2Login + client registration for Google

Exercises

  1. Why must users never type Google passwords into your login form?
  2. Scope vs consent — one sentence each.
  3. Access token vs ID token — which answers “who logged in?”
  4. What problem does PKCE solve?
  5. Why must redirect URIs match exactly?

Self-check

  2. Which Google screen asks the user to allow scopes?
  3. Name one OIDC scope commonly required for identity login.
  4. Is a SPA a good place to hard-code a client secret?
